The Core Mental Model

You don't tell K8s "start a container on server 3."
You say "I always want 3 copies of user-service running."
K8s figures out where, keeps them alive, restarts them if they crash, and scales them when traffic spikes.
That's the fundamental shift from Docker to Kubernetes.

Why K8s over Docker alone?
💀
Docker: container crashes → app down
K8s: auto-restarts in seconds, users never know
📈
Docker: traffic spike → one server overwhelmed
K8s: HPA auto-scales pods across multiple servers
🔄
Docker: deploy = restart = downtime
K8s: rolling updates — zero downtime, always
🖥️
Docker: you manage each server manually
K8s: treats 100 servers as one — you never SSH in
📦 Core Concepts — What Each File Does
📦
Pod — the smallest unit
🎯
What it is
A wrapper around one container. K8s never manages containers directly — only pods.
⚠️
Raw pods — never in production
If a raw pod crashes, it stays dead. Always use Deployment instead.
apiVersion: v1
kind: Pod # never use this in prod
metadata:
  name: user-service
  namespace: dev
  labels:
    app: user-service # 🔑 the label — glue for Service
spec:
  containers:
    - name: user-service
      image: gauravpal1828/user-service:latest
      ports:
        - containerPort: 3001
🚀
Deployment — the manager (always use this)
🔁
replicas: 2
Always keep 2 pods alive. Pod crashes → K8s creates replacement automatically.
🎯
selector.matchLabels
"I manage all pods with label app: user-service". Must match template labels.
📋
template
The pod blueprint. Every new pod is created from this template.
🔄
RollingUpdate (default)
Replace pods one at a time. Old pod killed only AFTER new pod is healthy.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
  namespace: dev
spec:
  replicas: 2
  selector:
    matchLabels:
      app: user-service
  template:
    metadata:
      labels:
        app: user-service
    spec:
      containers:
        - name: user-service
          image: gauravpal1828/user-service:latest
          ports:
            - containerPort: 3001
          resources:
            requests:
              cpu: "100m" # min needed
              memory: "128Mi"
            limits:
              cpu: "200m" # hard ceiling
              memory: "256Mi"
          envFrom:
            - configMapRef:
                name: user-service-config
            - secretRef:
                name: user-service-secret
          readinessProbe:
            httpGet: {path: /health, port: 3001}
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet: {path: /health, port: 3001}
            initialDelaySeconds: 15
            periodSeconds: 20
🚪
Service — the permanent door
🏨
Analogy
Hotel Receptionist
Traffic comes in → receptionist checks labels → routes to correct pod. Even if pods restart with new names, service always finds them by label.
apiVersion: v1
kind: Service
metadata:
  name: user-service
  namespace: dev
spec:
  selector:
    app: user-service # finds pods by this label
  ports:
    - port: 3001
      targetPort: 3001
  type: NodePort # local only, use Ingress in prod
🔐
ConfigMap + Secret — env vars
ConfigMap — safe to see
kind: ConfigMap
metadata:
  name: user-service-config
data:
  DB_NAME: shopeasy_dev
  DB_PORT: "3306"
Secret — encrypted
kind: Secret
metadata:
  name: user-service-secret
stringData:
  DB_USER: admin
  DB_PASSWORD: ShopEasy2026!!
⚠️
Critical: Name must match exactly
If configMapRef.name doesn't match metadata.name → CrashLoopBackOff

📈 HPA, Probes & Resource Limits
📈
HPA — Horizontal Pod Autoscaler
🍽️
Analogy
Restaurant calling extra waiters
Saturday night rush → call in 5 extra waiters. Quiet Tuesday → send 3 home. Pay only for what you need.
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef:
    kind: Deployment
    name: user-service
  minReplicas: 2 # never go below 2
  maxReplicas: 5 # safety ceiling
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          averageUtilization: 50
📊
What cpu: 124%/50% means
Pod demanding 124% of its 200m limit. Scale up fast. Scale down has 5 min cooldown to prevent flapping.
⚠️
HPA needs metrics-server
minikube addons enable metrics-server — without it CPU shows <unknown>
🩺
Probes — health intelligence
Readiness Probe — traffic gate
Container starts, app booting
Probe checks /health — 5s delay, then every 10s
DB not connected yet → returns 503 → probe fails
DB connected → /health returns 200 → probe passes
K8s marks Ready → load balancer sends traffic
Liveness Probe — restart trigger
App runs fine for days
App deadlocks — process runs but handles no requests
/health stops responding → liveness fails 3 times
K8s kills and restarts the pod automatically
🧠
Intelligence lives in your app code
Your /health endpoint must check DB connection — not just return 200. K8s just calls it, your code decides what "healthy" means.
⚖️
Resource Limits — boundaries
resources:
  requests: # minimum needed to schedule
    cpu: "100m" # 100 millicores = 0.1 core
    memory: "128Mi"
  limits: # hard ceiling — never exceed
    cpu: "200m" # 1000m = 1 full CPU core
    memory: "256Mi"
📐
requests = reservation
K8s uses this to pick which node to place the pod on. Node must have at least 100m free.
🚫
limits = ceiling
Pod tries to use more → K8s throttles it. Prevents one bad pod eating the entire node.
⏰ CronJob — Scheduled Tasks
⏰
CronJob — run tasks on a schedule
Cron schedule syntax
# ┌───── minute (0-59)
# │ ┌─── hour (0-23)
# │ │ ┌─ day of month
# │ │ │ ┌ month
# │ │ │ │ ┌ day of week
"*/1 * * * *" # every minute
"0 2 * * *" # daily at 2am
"0 8 * * 1" # monday 8am
"0 0 * * 0" # every sunday midnight
🚨
Always call process.exit(0)
Without it K8s thinks job is still running. exit(0) = success. exit(1) = failure → K8s retries.
💡
Real-world usage at Yodda
You write hello.js + the YAML schedule. DevOps deploys it. Your image must contain the file.
apiVersion: batch/v1
kind: CronJob
metadata:
  name: say-hi-job
  namespace: dev
spec:
  schedule: "*/1 * * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: say-hi
              image: gauravpal1828/user-service:latest
              command:
                - node
                - src/hello.js
          restartPolicy: OnFailure
// src/hello.js
function sayHi() {
  console.log("Hi! " + new Date());
  process.exit(0); // 🔑 required!
}
sayHi();

🔥 Hard-Won Lessons
💀
Mistakes you will make — remember these
🔴
ConfigMap name mismatch
configMapRef.name in deployment must EXACTLY match metadata.name in configmap.yaml. One typo = CrashLoopBackOff.
🔴
Creating raw Pods
Raw pods don't auto-restart. Always use Deployment. The only reason to create a raw pod is for learning — never production.
🔴
Working in default namespace
Always add namespace: dev to every YAML. Always add -n dev to every kubectl command.
🔴
HPA shows <unknown>
metrics-server not enabled. Run minikube addons enable metrics-server and wait 60 seconds.
🔴
Forgot process.exit(0) in CronJob
K8s thinks the job is still running. Container keeps running forever. Always call process.exit(0) at the end of your job script.
✅
/health must be intelligent
Your health endpoint should check DB connectivity. If DB is down, return 503. K8s will hold traffic until it recovers.
